# 元の本文
今回とくに盛んに議論された話題は、ComfyUI周辺のノード・ワークフロー不具合と、TTSモデルの実用性検証、LoRAの権利問題である。

### ComfyUI・ノード不具合と回避策
- comfyui-dynamicprompts は `${color=!{red|blue}}` のような変数宣言でシードを変えても以降の実行で同じ変数内容が固定されるバグがある。チャッピー（ChatGPT等）に聞いても解決せず、ソースを叩かないと直せないため別手段を探すべきとされた。回避策として was-node-suite の `Text Random Line` が推奨された（>>30, >>70, >>81, >>116）。
- ComfyUI v0.35から0.37へのアップデートでminimaxのrefが100秒ほど遅延する事象が報告された。高速化ノードが足を引っ張っている疑いがある（>>208, >>212）。
- フロントエンド v1.53.6 でwebp画像をドロップしてもワークフローが読み込めなくなる不具合が複数報告された。v1.52.7へのダウングレードで回避可能。デスクトップ版では発生しないとの報告もある（>>708, >>714, >>730）。
- 同 v1.53.6 で Fast Groups Muter/Bypasser (rgthree) の toggleRestriction が効かない問題も報告され、1.52.7を使い続けるべきとされた（>>874, >>944）。
- ComfyUIテンプレのワークフローで32の倍数調整によりアスペクト比がずれる問題があり、入力画像を32の倍数にクロップするか出力をリサイズで対応可能。入出力完全一致させても微妙にずくる報告もある（>>448, >>482, >>546, >>590）。

### irodori-TTS の展開と実用性検証
- irodori-TTS Large公開後、VRAM 8GB環境ではきつそうだが量子化モデルなら8Gでも使用可能。デフォのmodel Precisionがfp32だとVRAM 15.6/16GBになり長文でエラーが出そうなためbf16にするとVRAM 14/16GBに落ち、聞き比べても違いがわからないとされた。読み上げ精度はちょい下がり、メモリー使用量増加、レスポンスも落ちそうだが、参照音声は良くなっている。テキストエンコーダーがごっそり変わっている（>>186, >>189, >>191, >>195, >>216, >>232）。
- irodori-TTS-v4-Large は重く遅く、「こんにちは」の5文字で30秒かかったとの報告があり、V4smallよりV3の方が速いとの指摘もある。VRAM12GB環境ではポテンシャル引き出せず、Transformers 5以上必須とされた（>>264, >>330, >>385, >>659, >>717）。
- ComfyUIのIrodori Model Loaderでv4使用時にエラーが出る事例が複数発生。v3/v2では動作するがv4でエラーになる（>>568, >>604, >>611, >>635）。ComfyUIでv4が使えるのはlargeのみという指摘もある（>>677）。
- v4.1 smallで「アイドルマスター」「アイマス」と読ませると毎回違う謎単語になる不具合が報告され、元モデルでもHuggingFaceデモでも再現した。「アイドル」「マスター」単独は正常で平仮名にすると正常に読むため学習不足の可能性が指摘された。v4-Large-Quantized/int8-weight-onlyでは正常に出力された（>>983, >>985, >>986, >>996, >>998）。
- Gemini TTSで作成した音質の良い参照音声をirodoriに渡す用法や、ElevenLabs V4が日本語でGemini 3.8 Flash TTSより自然と評価され博多弁・大阪弁・名古屋弁・東北弁・沖縄弁をこなすとの報告もあり、クラウド型TTSサービスの品質向上によりirodoriの重要度が下がっている可能性が指摘されている（>>435, >>558, >>576, >>631, >>636, >>639）。

### LoRA学習・キャプショニングの課題
- Animaの部族語キャプショニングで「こっち向いてる後背位（1girl, 1boy）」の構図をキャプショニングする際、`netorare` や `voyeurism` を使うと覗いている3人目が遠景に描写され学習済み結果と一致しない。`facing viewer` や `straight-on` もしっくりこない。キャプショニング失敗で教師画像と全く別の生成結果になる症状として報告された（>>42, >>55, >>65）。
- Qwen Image 2.1（qie2.1）の画風LoRA作成は全然上手くいかず、AnimaやKrea2と比べて学習が難しい。`ai-toolkit` 初心者で使い方が間違っているのか不明。背景変更はすらすらならない（>>153, >>163）。
- MiniMax H3 のLoRAも難しいとの報告があり、画風と結合部分をいい感じにしたかったがプロンプトと既存LoRAでどうにでもなるかもしれないとの見方。minimax h3 ref2va lora学習検証屋が学習素材を2.5Dからほぼ2Dに置きなおして再学習したLoRAを公開した。動画参照やRefModでカバーできる可能性もありLoRAが必要ないか決めつけるのは早計とされた（>>53, >>59, >>72, >>90, >>137, >>140）。
- 学習時のタグ数平均化について、danbooruの二次創作イラスト上位は東方が圧倒的で次に艦これ、ブルアカだが、東方艦これは20年近く蓄積された玉石混交状態に対し、ブルアカはここ数年の比較的若いマスピ絵の絵師が多いため、平均化や選別をするとブルアカの割合が多くなるのではという見方。学習枚数は1キャラにつき最大200くらいで十分という意見（>>181, >>184, >>185）。
- minimax h3 ref2va 1f学習で、musubi-tuner紹介のTarget画像＋参照画像X枚を1セットにする手法を試したがRAM使用量が大量に溢れた。学習素材16組32枚、画像400、RTX4090、ブロックスワップ38、epoch100、学習時間3.5時間での検証では質感は影響×、形状は〇、モーションは△、プロンプトは〇とされた。精液がマヨネーズになるのは改善されず（>>334, >>926）。

### LoRAの権利・無断商用利用問題
- civitaiで公開したキャラLoRA（商用利用禁止チェック済み）をPatreonで金儲けに使っている人物を発見し対応を相談。まず本人にDMで「商用利用禁止、やめなければPatreonに連絡する」と伝えるべきとされた（>>813, >>845, >>990）。
- LoRAの証明は困難で、キャラLoRAなら雑に切り取った素材でも学習可能であり、自作LoRAを使っていると証明できない。画像メタデータにSHA-256値が残る等の証拠がない限り「自作」と言われたら詰む（>>841, >>872）。
- 商用利用禁止の主張は元モデルのライセンス次第。リアスやanimaライセンスが元ライセンスで商用OK・派生無効化OKの場合、商用禁止を押し付けると自分がライセンス違反になる可能性がある。既存キャラをLoRA学習して権利元を主張するのは狂っているとの意見（>>843, >>878, >>922）。
- 金を取ろうとせず「自分が作ったものを勝手に売られている」という主張に留めるべき。オリキャラでない限り著作権上どうしようもないという指摘も。スレ上では「公開した自分が悪い」「win-win」「裁判」など様々な意見が出た（>>829, >>834, >>837, >>990）。

### おっぱい・キャラクター描写の議論
- 今どきの中韓ソシャゲでおっぱいのデカさインフレし、昔のアニメの巨乳キャラは今基準だと並レベル。長乳化で巨乳の質量が2倍になった。ブルアカのアスナの影響が強く、`sagging breasts` や `huge breasts` を入れるとアスナの長乳の特徴の片乳ホクロが出てくる（>>155, >>156, >>179）。
- 胸の大きさの設定のないキャラは基本的に `small` 指定。二次は全体的にデカいから `medium` でもデカすぎることが多い。`small breasts, sagging breasts` の組み合わせも提案。元ネタがsmallやflatのキャラは原作準拠が至高だがあえて盛るのも良い。元ネタで巨乳枠だと二次創作では過剰に盛られ、原作準拠サイズの二次創作は皆無（>>149, >>151, >>157, >>165, >>166, >>182）。
- `flat_chests lives matter` 運動を提唱する声あり（>>160）。
- Krea2のサイズ指定で「flat」がsmallよりちょうど良いとの感想。サイズ表現として minute, tiny, very small, small, medium, large, huge, gigantic, enormous があり、incredibly等を付けるとさらに巨大化する（>>529, >>530, >>533, >>540）。
- minimaxでT2I生成時にプロンプトに関わらず乳首が出る問題が報告され、h3くんはbreastsに必ず乳首が付くと思っているためchestにした方が良いとされた（>>778, >>993）。

### AIエージェント・LLMのセキュリティと性能変動
- Claude Code等でローカルファイルを読み込まれないよう設定は可能だが過信は禁物で抜け道はある。エージェントの権限制限はエージェント自身が行っているものであり構造的にアクセスできない仕組みではない。厳密なサンドボックスには物理的にネットワークから隔離されたスタンドアローン環境が必要。Dockerはセキュリティ境界にはならない（>>924, >>958, >>961, >>973）。
- ゲームエンジン開発のコーディングとComfyUIカスタムノード作成にCodexを使用していただけでOpenAIアカウントが無効化された報告あり。ComfyUIのフォルダ（output等）をCodexに見られた可能性が指摘され、アウトロリ画像等があった場合BAN対象になりうる。健全絵のみでもメタデータのタグにロリが入っていてBANされた疑惑の騒動もあった。OpenAIのBANは基準が曖昧で泣き寝入りするしかない（>>734, >>764, >>784, >>793, >>799, >>832）。
- Claudeの場合、プロンプトに少女含みの内容があると「こちらで安全に治しときますね」と注意され、ロリ系NGワードをNegativePromptに自動で盛り込まれ、消すとハードコードすると怒られた事例あり（>>798, >>803）。
- 開発用AI母艦は分けるべき。Claude Codeで児ポフォルダを読まれ開発拒否された実例あり。開発用ComfyUI環境を別途用意するか別PCにするのが安全（>>857, >>881, >>823, >>825）。
- 6 Solは昨日より馬鹿になっているという複数の違和感報告。混んでる影響か自体がクソバカという見方。大手LLMのサイレントナーフ、計算リソース枯渇による下位モデルルーティングが常套手段（>>201, >>226, >>234, >>239, >>240）。

### ハードウェア・冷却・GPU選択
- 3060使用時、熱で落ちている気がするという相談。ケースファン5つ全部が最大回転1000rpm未満（前面3つ吸気、上面と背面排気）ではグラボ付近に新鮮な空気が流れていない可能性。グラボしばき倒す用途では厳しい。排気ファンの回転上げた方がよい。天面3連ファンの手前ファンの排気が奥2つより温度低ければ、手前を吸気にすると改善する可能性（>>27, >>31, >>37, >>62, >>172）。
- RTX 5090熱問題でDLSS5解説（1step Pixel Space Diffusion）で5090が600W超えるという話。コネクタを通る電力が600W・コネクタ温度が90度超える。5090で家燃えるなら買わない方が賢明。100万で5090 1枚（爆熱・故障の危険・VRAM 32GB）と100万で5080 3枚（ヒエヒエ・安全・VRAM 72GBただし48GBへの訂正あり）の比較試算あり。画像・動画生成なら同じ値段で5080を3枚の方がComfyUIで速くなる（マルチGPU対応が進んでいるため）。5090価格は今137万円で今更32GBに130万以上払う価値無いという意見（>>34, >>46, >>66, >>73, >>74, >>76, >>93, >>105, >>168, >>170）。
- ローカルLLM・画像・動画生成・TTS・3Dをやりたい場合、理想はRTX PRO6000だが高額。5060tiまたは5070tiの2枚積み＋メモリ搭載で妥協が現実的。Mac Studioハイエンドは要件を満たすが最適化されておらず不便。動画回せるPCがない状態ならVRAM16GBデュアル＋メモリ256GBを推す声あり。数百万の買い物の前にレンタルGPU（runpod等）で試すべき（>>956, >>966, >>981, >>982）。
- 動画生成のVRAM問題で、VRAM99%で電力消費低・温度低いのにじわじわ進む現象。VRAM領域分断またはOOM限界。再起動かStep数/解像度下げで解決。4070Tiで0.6MP15秒、1MP10秒で発生（>>359, >>366, >>371, >>379, >>384）。

- irodori-TTS v4系は精度向上の一方で推論速度・VRAM消費・特定単語の異常読み上げなどの課題が顕在化しており、ElevenLabs等のクラウドTTSの品質向上が相対的な位置付けに影響を与えている。
- LoRAの無断商用利用問題では、元モデルのライセンス次第で商用禁止主張自体が違反になりうる点や、LoRA利用の証明が困難な点が浮き彫りとなった。
- OpenAI・Claude等のAIエージェントにローカルファイルを読まれた結果アカウントBANや開発拒否に至る事例が複数報告され、開発用環境の物理的隔離の必要性が確認された。
