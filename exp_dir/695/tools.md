## ComfyUI：Sparse Attention系ノードの最適化と移行

comfy公式のcomfy-kitchen attentionおよびBlock Sparse Attention（後にModel Sparse Attentionに改名）への移行が進んだ。Sage AttentionやSol Attentionの削除により起動が大幅に早くなり、VRAM 12GB/16GB環境では「Loader - ModelAttentionBackend（comfy kitchen attention）- Block Sparse Attention（top-k(SLA)）- MiniMax H3 Chunk FeedForward - ModelSamplingMiniMaxH3」が鉄板フローとされた。Sage+sol+spectrum環境で50分かかっていた処理の最適化も議論された。

Block Sparse AttentionのselectionをSol-Attnからtop-k(SLA)に変更すると、不自然に変化していた固定背景が変化しなくなり、Sol Attentionが原因だった可能性が指摘された。作画崩れの修正にはstep値ではなくselectionをtop-kにしkeep percentを20まで上げる手法が推奨された。block sparse attentionにはメモリリークバグがあり低VRAM環境でOOMが発生していたが、9:33のコミットで修正された。一方、生成中に時々ComfyUIごと落ちる問題も報告され、古いノードから新しいノードへの入れ替えが必要とされた。

comfy kitchenは静止画モデルでもsageより僅かに早く、約1ヶ月前にあった構図が変わる問題も修正済みとの報告がある。ただしsage attentionを起動オプションに入れると何かの画像生成機能がしなくなる現象も報告された。

ノード名の変更があり、検索で「Block Sparse Attention」が見つからない問題が発生。ノード名が「Model Sparse Attention」に変更されていた。nodes_sparse_attention.pyをAIに読ませてパラメータ解説させる運用が紹介された。類似名ノードが多数存在し、後ろに(top-k)と付いているノードを使用しているケースもある。

Comfy CompilerのMMH3等でのメモリ周り最適化が実施されたが、--disable-comfy-compilerで起動落ちを防止する回避策も報告された。更新後にノードも更新があり、項目に対する入力値がズレる現象が発生。ノードを設置し直すことで対応した。

## ComfyUI：VAE周りの高速化

Fast VAEかTRT VAEでVAEの処理を軽くする提案がなされた。TRT VAEを使用した結果、VAEのint8convrotと速度があまり変わらなかったが、生成サイズが大きい方が恩恵を感じられるとの見方がある。TRT VAEの精度はFP16であり、int8 convと速度が変わらないならTRT VAEの方がお得とされた。環境によってはTRT VAEがint8 conv使用Fast VAEより少し遅いためTRTを使用しているケースもある。Fast VAE Comfy V0.31では爆速で問題なく動いていたが、最新版に更新したら生成物がやたら暗くなる不具合が報告された。MMH3でVAE Decode時間短縮に有益な情報があるとの言及もあった。

## ComfyUI：ワークフロー管理と運用

現在話題になるモデルのワークフローはComfyUIのテンプレに用意されるようになり、以前のように自分で組むかCivitai等でクソデカワークフローを落として使うしかなかった時代と比較して便利になった。H3のcomfyui公式テンプレートにはマルチフレーム参照テンプレートが新たに追加され、T2V, I2V, Ref2Vと計4つになった。自作ノードを使っていると他人に公開しづらく、公式WFに戻す運用でやり直しをしているユーザーもいる。ワークフローがぐちゃぐちゃになるためサブグラフを使うべきという指摘や、メモ帳代わりにプロンプトノードをぺたぺた貼り付けるケースが原因として挙げられた。tadaupは一定時間経つとメタデータが消されるため、ワークフロー付きの画像がアップされていても消えている場合がある。

miniMaxH3のLoRA loaderノードは高速化ノードの前後どちらに置くべきか実際に比較検証され、前にLoRAノードを入れた方が20秒速かったという報告がある。comfyuiでpower lora loaderではなくwebuiのようにtext入力でloraを使うカスタムノードについての質問があり、impact packのimpact wildcard encodeに該当機能があると回答された。

ComfyUI終了後もCPUに負荷が残りPC再起動しないと直らない問題が報告され、pythonプロセスが残っている可能性があるためタスクマネージャからpythonを終了すれば良いとされた。H3使用中に本体がKILLされる問題について、100件更新ごとに最新クローンする設定で治った可能性が報告された。

ComfyUIをCodexで丸ごと管理しておりCodex依存になっているという運用報告もある。ComfyUIでローカルLLMを導入しようとしたところ「This violates core safety guidelines regarding sexual abuse and violence.」のエラーで使用不可となり、非検閲モデルを使うべきとされた。

## Codex / チャッピー：エージェント運用とツール自動作成

Blenderプリビズを動画AI参照に使用する手法をCodexに試させた結果、ある程度まで可能だった。分業体制としてAstraで監督役、TerraでBlender操作、LunaでMinimaxへのキュー投入役を担当させたが、Plusプラン5時間枠で数秒カットが精一杯だった。全任せはトークン消費がマッハのため、定形作業のスクリプト化と推論作業の切り分けが必要とされた。512x288の低解像度で位置関係・カメラのみ読ませる手法で、5秒動画が140s→280s、15秒動画が700s→1000sに増加するが構図制御の見返りとして許容範囲とされた。

様々なAIをインストールしているとどこに何が入っているか迷子になり、outputする画像や映像もAIによって場所が異なり管理が混乱する。WSLのホーム直下に起動スクリプトを置く方法や、エクスプローラーのショートカットにフォルダを登録する方法が挙げられている。AIが作るツールは指示しなくてもwebpにすべて対応しているため楽ちんという感想。Pixivはwebp投稿不可のため、webpで普段生成しておけばウッカリメタデータ流出対策になる。jpgで出力していれば渋投稿でメタデータ流出を気にしなくて済む。sikiでLvなしNGする設定の登録方法も説明された。civitaiの画像ランダム解析失敗で一生他人に表示されないバグは致命的とされ、civitaiで検索するよりcivarchiveで検索して移動した方がいいとの指摘。

## 総評

1. ComfyUI公式のSparse Attention実装（comfy-kitchen / Model Sparse Attention）がSage AttentionやSol Attentionを代替する鉄板フローとして定着しつつあるが、ノード名変更やバージョン管理の不整合（安定版と開発版の機能差）により移行時の混乱が継続している。

2. Codexやチャッピー等のコーディングAIを用いたツール自動作成が実用段階に入っており、Blender操作・リップシンクノード自作・LoRAマージUI作成・自動キャプションツール構築など、生成AIパイプラインの各工程を自動化する動きが活発である。同時にトークン消費とPC操作への安全性懸念が課題として挙げられている。

3. VAE高速化（TRT VAE / Fast VAE）およびアップスケール処理において、速度と品質のトレードオフ調整が継続課題であり、Fast VAE更新による暗化不具合や純正アップスケーラー未提供などの具体的な障害が報告されている。

4. 複数AI環境のインストール先・出力先混乱が構造的な問題として認識されており、WSL起動スクリプト集約やエクスプローラーショートカット等の運用対策が共有されている一方、webp/jpgによるメタデータ流出対策もツール選択の要件に影響している。
