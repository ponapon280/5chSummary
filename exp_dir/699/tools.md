## ComfyUI

### ワークフロー構築・運用
- **プロンプトエンハンサー・LLM連携**: テンプレWFのサブグラフ内LLMや、ComfyUI謹製のTextGenerateノードを用いて、ふんわり日本語で指示すると良い感じのプロンプトに仕上げるWFを構築可能。QI2.1用のPrompt Enhancer組み込みWFも配布され、30秒程度でプロンプトが生成され常用範囲内。生成プロンプトが中国語になるがQwen的にはその方が良いらしい。LLM経由でプロンプトを作成する際、RegexExtract node (All Matches)で抽出する手法も提示されている。ComfyUIのHFにはプロンプトエンハンサー用のTE（qwen3.5テキストエンコーダー）が追加されており、i2iとt2i用がある。またBenjiニキのカスタムノードも便利だが、max_length=24,000の処理に1時間近くかかる不具合報告あり。
- **古いWFの修復**: 8ヶ月ぶりに復帰し過去のWFを読み込むと使えないノードが多い問題に対し、動かないWFをAIエージェント（Codex等）に放り投げて同等機能のノードを作らせてWFを動かす方法が提示された。ただしComfyUIでCodex Astraを使うのは勿体なく、GPT Solで十分。
- **モデル切替**: Ref2VA用のWFのモデル部分を「If/Else Switch」ノードで切替式にしてFL2VAモデルを使用。FL2VAモデルにRef2VA用のノードを使って参考画像を渡してもちゃんと従ってくれる。
- **OpenPoseスワップ**: QI2.1でOpenPoseノードを挟めばポーズスワップが完璧にできた。Minimax ImageStudioでも同じようにできる見込み。
- **音声リファレンス**: FL2VAテンプレWFにrefmodを挟むことで、irodoriで作った音声をそのまま映像に出力できる。
- **VRAM節約**: `--listen 0.0.0.0`にして別端末からComfyUIを操作すればVRAM節約可能。

### 選定理由
- 最新モデル（Qwen-Image-2.1等）にいち早く対応するため。モデル公開前から対応済みであるため、新モデルをすぐ試したいならComfyUIを使わざるを得ない。WebUIから離れられない層はNeo等を使用しているという分析。

### デフォルトWF・起動オプションの問題と対処
- QwenのデフォルトWFではシードが固定されており毎回手動変更が必要。サブグラフ展開→Kサンプラーのシードを「randomize」に変更する必要がある。スレ上の感想として「絶妙に嫌がらせみないに使えない」。
- 起動batに`--fast fp16_accumulation`を入れるとvaeをint8にした際にデコード爆速になり画質も見分けが付かない。ただし環境によってはエラーでPC再起動するしかなくなる事例も。ComfyKittinAttentionと競合しプロンプトガン無視になるバグが発生するため、`fp16_accumulation`はKJ NodesのModel Patch Torch Settingsで個別に設定する方が安牌。
- ComfyUIをアップデートした際、MiniMax H3 Reference to Video等のノード入力要素追加がバグる問題。タブ移動時にFast Muter等がおかしくなる不具合はフロントエンドを1.52.7に下げると直った。H3で生成時間が異常に延びる問題（10秒生成に90分等）は最新版で緩和される。
- attention系ノードが低速化の原因になることがあり、対象環境ではsol attnもkitchin attentionも外した方が明確に早くなり高速化ノードはspectrumだけでよくなった。

### 自作ノード・カスタムノード
- シチュエーション固定でカメラアングル10回ランダム生成→次のシチュ等、リスト順番指定や別リストのランダムシャッフルを選択可能にした自作ノード。wildcard系と異なり柔軟な指定が可能。
- 画像サムネイル右クリックでエクスプローラーを開く機能が標準でないため自作した機能に対し「有能」の反応。
- 複雑なカスタムノードのデバッグにAstraを使用する事例がある。

- comfyはMCPを使って動かすとトークンが安く済む。

## Codex / Astra / Sol / Luna / Claude (コーディングAI運用ツール)

### タスク別使い分け
- **Astra**: 難易度の高いタスク（システムやゲームのフルスクラッチレベル）限定。Blenderでリモートモデリングさせたら10分ちょいで100%から0になった。Computer Useを使うようになってからトークンの減りが爆速でx5だと全然足りない。リモート操作させると秒速でトークンが溶ける。WorkとCodexでしか使えない。Astra High以上は大規模でぐちゃぐちゃなソースコードをレビューする用途。Pro契約すればAstra（6）Proが呼べる。
- **Sol**: カスタムノード作成・ウェブアプリ作成にはSolで十分。会話系ならLunaでも十分。普通の作業はSol、コードレビューはAstraという使い分け。Sol Highは余計に複雑に思考し出力も肥大化しコストがかかるため、デバッグや要件がはっきりしているものはLowの方が良い結果になりやすい。GPT6 Sol HighよりGPT5.6 Solの最大の方が性能が良い気がする。
- **ChatGPT連携**: Chat側でWeb経由でGithub参照して設計をProモードで作業させ、Codexに渡す指示をChat側で細かく出すと実装側の負担が減る。CodexデスクトップだとChat ProのログをそのままCodexに突っ込める機能がある。

### Codex
- Proプランでクレジット消費がなかなか減らない。週間リセット機能がありリセット権はプラン変更しても持ち越せる。カスタムノードや生成周りのアプリ作成程度なら5倍でも過剰。システム開発で常に23個のプロダクトを動かしOpenClawも毎日50万トークンくらいと1000回程度の呼び出しをしている。CodexやClaude Code自体がバグっていてキャッシュトークンが効かない時もある。

## 総評
1. **ComfyUIの最新モデル対応の速さがツール選定の最大理由であり、WebUI系（Forge Neo等）は最新モデル対応の遅れからWebUIから離れられない層の留まり場所にとどまっている。**
2. **コーディングAI（Astra/Sol/Codex）はタスク難易度とトークン消費のバランスで厳密に使い分けられており、カスタムノード作成程度ならSolで十分というコンセンサスがある一方、Computer Useやリモート操作はトークン爆発の危険があるとされている。**
3. **LoRA学習ツールはQwen2.1やMiniMax H3といった新モデルの多層化・複雑化によりVRAM要求が厳しくなっており、4090でもギリギリまたは不可の状況で、低VRAM環境向けにはFizgigのような選択肢が模索されている。**
4. **ComfyUIの起動オプション（--fast fp16_accumulation等）やattention系ノードは高速化に寄与する一方でバグや低速化の原因にもなり得るため、個別ノード設定での制御や環境に応じた取捨選択が必要とされている。**
