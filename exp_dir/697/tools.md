# 元の本文
本次とくに盛んに議論された話題はComfyUI本体のバージョンアップに伴う高速化・メモリ効率改善と、Codexやチャッピー等のLLMエージェントを用いたカスタムノード自作・改造・トラブル解消である。

※以下のレス番号は元スレの通し番号とは限らない。

## ComfyUI本体・実行環境

- **バージョンアップによる高速化とメモリ効率化**: 最近のComfyUIは各種高速化・メモリ効率化が本体にマージされており「更新一択」とされる（822）。v0.36.0でVAEの高速化が入り更新するだけで生成が快適になる（822, 825）。RAM使用量が大幅に下がったとの報告もありチャンク読込が効いている可能性がある（826）。ComfyUIをアップデートしたら生成が凄まじく速くなったという報告もある（589, 592）。
- **動画生成における最適化**: ComfyUIの最適化により動画生成はVRAM容量ゲーではなく潤沢にRAMを使った処理速度ゲーになっており、RTX Pro 6000と5090の差は微差になるというスレ上の見解がある（434）。pro6000はVRAM 96GBのおかげでモデルもTEもbf16で処理できる利点がある（461）。ただしComfyUIは動画を複数のRAW画像としてメモリに全展開してから処理するため、30秒の動画だと解像度次第では60GB消費することもある（672）。
- **起動エラーの修正**: ComfyUIの起動にエラーが混じり遅くなった際、LLMのFable 5.1にログを見せるとエラー修正と不要ノード削除をPowerShellのコピペで行い、起動時間を30秒以上短縮できた（531）。
- **ConnectionResetErrorの原因**: 生成終了後に`ConnectionResetError:[WinError 10054]`が頻発する事象について、原因はComfyUIを開いているブラウザのタブが裏に回るとスリープしリアルタイム進捗更新用の接続が切断されるため。タブを呼び出せば自動再接続され、実害はプレビューに最新生成結果が表示されない程度（896, 898, 900）。
- **NVMeSSD自動判定プルリク**: Comfy mainにNVMeSSD使用を自動判定して`--fast-disk`が有効化されるプルリクが入った。メモリに詰められるだけ詰める挙動が緩和される見込み（829）。
- **デフォルトワークフロー変更**: ComfyUIのデフォルトワークフローがSDXLからz-image-turboに変更されている（642, 644）。

根拠: 434, 461, 531, 589, 592, 642, 644, 672, 822, 825, 826, 829, 896, 898, 900

## LLMエージェント・コーディングツール（Codex / チャッピー等）

- **カスタムノードの自作・改造**: Codexに希望するカスタムノードを作ってと頼むと本当に作ってくれる。ワークスペース外のファイルは書き換えないが作業内容によっては読み取りに行くのが怖いという懸念もある（867）。ちゃっぴー（AI）に相談するとウキウキでノード改造してくれる（878）。AIエージェントを使えばあまり知られていないモデルやカスタムノードを探したりもできる（603）。ちまちまいじって最適化して育てる感覚はCodexに任せていたら味わえないという意見もある（233）。
- **キャプション精度のデバッグ**: 従来TaggerやLLMで自動出力しただけではクソ精度だが、生成してみておかしなところをCodexと相談してキャプションの付け方をデバッグするとほんとに反映される。Krea2のテキストエンコーダーが賢いのでマジでキャプションゲーになっている（907, 909）。
- **ストレージ消費**: Codexをゴリゴリ使うようになったら意外とストレージ空き容量がマッハで減っていくことに気づく（955）。チャッピーはノウハウが蓄積されており精度が高いとの評価（234）。
- **uv (Python仮想環境ツール)**: pipではなくuvでpython仮想環境を作るようにしたら重複分を一つにできて容量減らせるし、使われていないキャッシュだけ削除できたりしてSSDの寿命的に優しい（949）。uvのキャッシュがばちくそ溜まっていたほか、windowsの休止状態を無効化してファイルを消したら130GB浮いた（954）。
- **APIキー管理**: AIエージェントを使う際.envや環境変数にAPIKeyを置いても内容流出のリスクがある。対策としてAPIキーは流出前提で設計し定期的に失効させたり権限を制限して使うことが推奨されている（591）。

根拠: 233, 234, 531, 591, 603, 867, 878, 907, 909, 949, 954, 955

## ComfyUI用カスタムノード・ワークフロー機能

- **Attention系ノード（ComfyKitchenAttention / SolAttention / sol-attn）**: 動画生成において5090環境でもこれらを使わないと20分超かかる問題が指摘され、使用すると時間が半分近くなる。劣化具合は不明（408）。完全一致を要求するプロンプトだと間違いが目立つがアバウトなプロンプトだと劣化は気にならない（409）。ただしminimaxの動画でテストのため一度高速化関連を切ったら何故か生成がバカっ早くなった。sol attnが変な処理をしていた模様。spectrumだけにしてもかなり高速生成できた（887）。
- **Spectrum / block sparse attention**: Spectrumは動くが機能しない、stepを飛ばしてくれないという不具合報告がある（273）。block sparse attentionノードでSpectrumがstepを飛ばさなくなる問題が発生したが原因はWindowsの改行コードだった（273, 284）。
- **Extender**: New Projectで1clip分の画像とプロンプトを用意して実行するとプロンプトが空になり空のclipが3つ発生する不具合が報告された（275）。Refワークフローを検証しPrompt package Bridgeをバイパスしたらうまくいった。このノードにデフォルトでstringsノードが3つ繋がっておりその数に合わせてクリップを作成していたことが原因と推測されている（297, 312）。
- **RefMods（ノードパック）**: キャラLora作成用画像22枚とIrodori-TTSで作ったボイスサンプルから10秒で6MBと300KBのsafetensorsファイルが生成された。6MBのファイルでここまで再現できるならお手軽Loraとして使えそう。Media LoaderとPrompt Builderが便利（904, 905）。精度が上がって生成時間も短くなるというかなり良いノード。ref2vaモデルで参照をmaxで読み込むと生成に時間がかかりすぎて萎えるがRefModsで解決できる可能性（906, 912）。
- **公式ループノード・Context loop系**: 公式のループノードが登場したがどう使うのが賢いかという話題が出ている（522）。Context loop系のノードが毎日のように追加されExtender等の機能も出てきているがAIに状況を聞くと「WFをイチから作り直したほうが良い」と言われる状態が続いている（214）。context loopでシーン毎のSEED値をキュー投入ごとに変えたいが`-1`を入れるとエラーが出るという不具合もある（872）。
- **PNGinfo相当カスタムノード**: ポジ・ネガ・Lora・ステップ・CFG等を表示・コピーするカスタムノードの需要があるが既存で良いものが見つからない状況（125, 136, 151, 154）。
- **ECHOCheckpointLoaderSimple / SetSubseeds**: インストール方法を探すが検索してもGitHubに出てこない（877）。`SetSubseeds`および`SetSubseeds_Image`は見つからずチャッピーに聞いても分からなかった。GitHub内で検索するとTensor.Art由来の内部ノードの可能性が高い（881, 886, 893, 894）。
- **ComfyUIのファイル参照仕様**: ファイル名に使う文字列（`%ノード名.プロパティ名%`など）が一律的に参照できず名前が微妙に違ったりして面倒であるという不満。プロパティパネルに一意に定まる参照名を明記してほしいとの要望がある（387）。

根拠: 125, 136, 151, 154, 214, 273, 275, 284, 297, 312, 387, 408, 409, 522, 872, 877, 881, 886, 887, 893, 894, 904, 905, 906, 912

## 動画生成ワークフロー関連ツール（ComfyUI上の高速化モデル・VAE等）

- **vsa4step (minimax_h3_fastvideo_vsa_datafree_1300step_4step_int8_convrot)**: FastH3よりも大体良い結果が出たとの報告（812）。速さと品質両立していてゲームエンド的。適当に入れたらRef2vでも使えた（844）。3stepの爆速としてはすごいがLarry 6stepよりは品質が明確に悪いというスレ上の評価（874）。
- **FastH3 V2**: 追従性と一貫性が良い。0.6MP 10s 8stepsでTurbo 82.04s、FastH3 V2 93.84s。V1は4step、V2は8step（699, 712）。ただし肌がツヤテカでプラスチックっぽくなる（729）。出力がかなり変わる上速さも大したことないとの否定的な意見もある（810）。ref2va非対応（709, 719, 819）。
- **VAEハッシュ差異**: VideoのVAE(int8)のハッシュを確認したところComfy公式とFastH3は同じだがKijaiのint8とは別物。VAE周りの高速化はUIのアップデートだけでは不十分でファイルもComfy側に寄せた方が良い可能性（780）。mmh3のvaeデコードが速くなったためComfyUIの更新が必要（716）。kijaiが上げた新しいint8_conv VAEは以前より良くなっている模様（908）。
- **DaVinci Resolve**: ComfyUI一発での長尺生成はクオリティが低くなるためDaVinci Resolve等の編集ソフトで個別動画を繋ぐ方が良いという意見あり。ただしcontext loop系ではシームレスな繋ぎが実現できている（217, 221）。

根拠: 217, 221, 699, 709, 712, 716, 719, 729, 780, 810, 812, 844, 874, 908

## 画像ビューワ・生成画像管理ツール

- **Zippla**: webpの閲覧が遅すぎるため自作アプリに移行（164）。画像の星レート引き継ぎ元として言及（251）。
- **mimageViewer**: Zippla後継として良さそうだがanimated webpの読込が遅い（187）。
- **Neeview**: 見開き画像ビューワだが細かい部分が合わず徐々に重たくなる（172, 175）。使用中との声もある（261）。
- **Irfanview**: 軽い。shift+wでウィンドウサイズ固定。バッチ処理をGeminiが推奨（188, 191, 192, 212）。使用しているユーザーが他にいて嬉しいという声（236）。
- **Eagle**: 有料の管理ソフト。ComfyUIのsaveノードからの自動保存をチャッピーに頼んで実装した報告がある（247）。過去におすすめされて購入したものの放置していたが慣れると良いとの評価（247）。
- **自作ビューワ**: レス251のユーザーが「webp軽い・zip開ける・zipplaからの星レート引継ぎ可能」の自作ビューワを公開。レス296のユーザーも既存ビューワのメモリ影響や動作不良を理由に自作した。Codexで作成した画像ビューワの使い勝手についての言及もある（252）。
- **その他**: hamanaは軽くて現役（175, 180）。まっしぐらはシンプル伊豆ベストで長期使用（181）。マンガミーヤは軽くて機能が揃っているため使用継続（213）。bandiviewの購入検討声あり（257）。ACDSeeに満足しているユーザーがいる（252）。qViewも使用されている（253）。

# 総評

1. ComfyUI本体のアップデート（v0.36.0）でVAE高速化・RAM使用量削減・チャンク読込等のメモリ効率改善が入り、更新するだけで生成が快適になるという実益のある改善が報告されている。動画生成はVRAM容量ゲーからRAM活用の処理速度ゲーへ最適化が進んでいる。
2. Codexやチャッピー等のLLMエージェントがカスタムノード自作・改造・不具合調査・キャプションデバッグ・画像ビューワ作成に実用レベルで使われており、ComfyUIのエコシステム拡張においてエージェント活用が常态化している。
3. Attention系ノード（sol-attn等）やSpectrum等の高速化カスタムノードで不具合や異常動作が報告される一方、vsa4step等の高速化モデルが速さと品質を両立しつつあるという評価が出ている。VAEのファイル差異による高速化阻害も指摘されている。
4. 画像ビューワ分野では既存ツール（Zippla・Neeview等）の不満から自作ビューワを作るユーザーが複数おり、その際にもCodex等のAIコーディングツールが活用されている。ストレージ消費対策としてuvによるPython仮想環境管理が有効とされている。
