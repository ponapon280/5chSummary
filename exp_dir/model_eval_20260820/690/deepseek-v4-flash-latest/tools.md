# スレッドログに基づく生成AIツール利用に関するレポート

## 1. はじめに

本レポートは、生成AIに関するスレッドログから抽出した「ツール」に関する話題をまとめたものです。話題の中心は、画像生成・動画生成・LLM（大規模言語モデル）の実行環境や支援ツール、およびそれらの利用における課題や選定理由です。

## 2. 主要なツールカテゴリと話題の概要

### 2.1. ComfyUI（ワークフロー実行環境）

ComfyUIは、画像生成や動画生成におけるワークフロー実行環境として、多くの話題で登場しました。特に、以下の点が主要なトピックです。

- **カスタムノードの対応状況**: IrodoriTTS v4ではComfyUIカスタムノードに未対応であることが報告されました（>>80）。また、civitaiで配布されているワークフローや、dasiwa氏配布のワークフローに専用カスタムノードが必要であるとの議論がありました（>>163, >>166）が、公式テンプレートの方が優れているとの意見もありました（>>166）。
- **メモリと生成速度**: メモリ増設が動画生成・画像生成の速度に与える影響についての報告がありました（>>195, >>197）。4枚刺し4000MHzでの生成速度は誤差数秒程度と報告されています。
- **高速化技術（comfy-kitchen）**: 「comfy-kitchen」のPR#117での更新と、kijai氏による高速化（sol_attn_minimax_v3.pyノード）が注目されました（>>189）。このノードの利用には、ビルド済みwheelを使用するか、自分でコンパイルする必要があると報告されています（>>190-194）。
- **高速化ノードの性能評価**: ComfyUIで「Sol-Atten (MinMax) VideoProcess」サブグラフを利用したところ、Sage Attentionよりも遅いという報告がありました（>>210）。また、RTX5080環境でのcomfy-kitchenやPR#117の恩恵について、Sage Attentionとの比較が行われました（>>225）。
- **外部LLM連携（Ollama）**: ComfyUIとcomfy-ollamaを連携してLLMでプロンプトを生成し、画像生成を行うワークフローが紹介されました（>>229）。しかし、VRAM溢れの問題が報告され、OllamaのモデルはComfyUIを終了しても解放されないため、keep_alive引数（"0s"）を追加する方法が共有されました（>>245, >>251）。
- **トラブルシューティング**: VRAM解放ノードが無いためにComfyUIを再起動しても問題が解決しないケースや（>>236）、バックエンドでComfyUIを利用した自作ツールの公開予定（>>305）、Context Loopノードを用いたMV制作報告（>>378）なども挙げられました。
- **画像生成の不具合**: BIOS設定変更後にComfyUIでの画像生成に不具合が発生したという報告（>>935）も見られました。

### 2.2. その他のワークフロー／実行環境

- **SD WebUI**: 「未だにSD WebUIから逃れられない」というユーザーの利用報告がありました（>>304）。
- **Forge Neo**: Anima 3.8Bや2.9Bを利用する際の実行環境として登場しました。性能面ではプロンプト追従性が向上するものの、層置換によるLoRA非互換や生成速度の低下、VRAM消費の増加が報告されています（>>445-490, >>602, >>605）。複数キャラクターの混ざりにくさが改善される一方、エロシチュエーションではLLMキャプションの限界も指摘されました。

### 2.3. LLM（大規模言語モデル）実行・活用ツール

- **Ollama**: 上記ComfyUI連携に加え、単独でローカルLLMを実行する用途で話題になりました。Qwen3シリーズ（3.8-27B）等の利用がありました（>>656, >>465）。
- **FreeToken**: 新しいLLM実行技術として注目されました。VRAMが足りない場合でもDRAMからストリーミングで高速実行できる点が革新的で、従来のllama.cppよりMoE領域を動的にVRAMに配置する点が優れると評価されています（>>465, >>491-565, >>891）。ただし、実装に制限があり、使い所が難しいとの声もあります。
- **ローカルLLM環境構築**: プロンプト生成のためにローカルLLMを利用する話題（>>768, >>773）や、Animaへの自然言語プロンプト生成に利用されるケースが報告されました。また、「Deno Local LLM Loader」という、ローカルLLMをロードしてH3のテンプレートに沿った英語プロンプトを生成するノードの紹介もありました（>>316）。
- **クラウドLLMとローカルLLMの比較**: ローカルはオープンモデルを選び放題で、無検閲のLLMを利用できる点が利点として挙げられました（>>836, >>841, >>852）。一方、クラウドLLMはサービス提供側の気分次第で機能が変わる可能性があり、ローカルの安定性が強みと述べられています（>>841）。性能面では、特に日本語のLLMはクラウドに大差で負けているとの意見（>>844）がある一方、クラウドでuncensoredモデルを利用できるサービスも存在するとの指摘もあります（>>850）。
- **エロプロンプト生成**: ローカルLLMではクラウドでは拒否されるエロ生成が可能で、どこまでも変態になれるという意見（>>848, >>852）があり、特定のプロンプト生成に利用されています。Grokはエロプロンプト作成に便利とされつつも、ピークタイムの制限や、girlをwomanに置き換える等の工夫が必要という報告があります（>>474, >>854）。

### 2.4. 画像・動画編集・生成支援ツール

- **Aviutl**: モザイク処理や出力時の問題についての報告がありました（>>153, >>165）。x264guiEx出力設定の調整が必要とされています。
- **超解像拡大（アップスケーラー）**: 超解像拡大技術の認知度や、その実用性、限界に関する議論がありました（>>932, >>936, >>937, >>949, >>962, >>968, >>974, >>985）。映像業界での評価についての言及（>>953）や、Topazのアップスケーラーの知名度（>>961）に関する意見も出ています。単純なアップスケールの実例（>>962）や、アップスケールモデルによる勝手な解釈の問題（>>985）が報告されました。
- **ワイルドカード拡張**: Chromeのワイルドカード拡張や、A1111のダイナミックプロンプト機能がランダム性付与の手段として紹介されました（>>740, >>746）。
- **その他**: 画像編集ツールとしてのクリスタやAffinity（>>811, >>816-817）、疑似立体視を実現する「Autodepth Image Viewer」（>>424）、クラウドレンタル（RTX6000）でのLoRA作成検討（>>580）などが登場しました。

## 3. ツールが選ばれる理由

スレッド内で言及されたツール選択の主な理由は以下の通りです。

- **ComfyUI**: カスタムノードやワークフローの自由度が高く、コミュニティによる拡張が活発である点（>>189, >>225）。
- **LLM実行技術（FreeToken等）**: VRAM等のリソースを動的に活用できる革新的な仕組み（>>465, >>491-565）。
- **ローカル環境**: 無検閲モデルを選び放題で、エロ生成の自由度が高い点（>>836, >>852）。
- **クラウドLLM**: 特にプロンプト生成の質が高く、エロ生成（grok等）にも利用できる点（>>474, >>854）。
- **Aviutl**: モザイク処理の用途が広く、広く使われている点（>>153, >>165）。
- **プロンプト支援ツール**: プロンプト作成効率化のため、LLM（ChatGPT、Gemini、Claude、Grokなど）や「Qwen 3.8ベースのプロンプターノード」等が活用されています（>>124, >>931）。

## 4. 注目すべき課題

- **VRAM管理**: ComfyUIとOllamaの連携におけるVRAM溢れ問題は、keep_alive設定の調整が必要となるなど、ユーザー間でノウハウ共有が必要な課題として挙げられました（>>229-251）。
- **高速化技術の利用難易度**: comfy-kitchenのPR#117等、高速化ノードの利用にはコンパイル等の専門知識が必要な場合があり、導入のハードルとなっています（>>190-194）。
- **LLMのループ問題**: 特定のLLM（qwen3:8b）にて、過学習によるプロンプトのループが報告されました（>>656）。
- **ツール統合の難しさ**: 複数のツール（画像生成、LLM、動画生成等）を連携させるワークフローの構築は、各ツールの特性を理解する必要があり、複雑化する傾向にあります（>>931）。

## 5. まとめ

本スレッドでは、ComfyUIを中心としたワークフロー環境の高度化と、LLM（OllamaやFreeToken等）を活用したプロンプト生成の効率化、およびクラウドとローカル環境の使い分けが主要なツール関連トピックでした。ユーザーは性能や自由度を追求する一方で、VRAM管理やノード導入の難易度といった実運用上の課題にも直面しており、コミュニティ内での情報共有が活発に行われている実態が確認できます。
