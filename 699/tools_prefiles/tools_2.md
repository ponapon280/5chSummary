ログから、生成AIの「ツール」（UI・ノード・補助LLM/VLM・画像処理・学習環境）に関する話題だけを抜き出しました。画像生成モデルそのものの性能・比較・作例は除外しています。Qwenは画像生成以外（VLM・テキストエンコーダ・LLM）だけ残しています。

## ComfyUI / WebUI / Forge Neo

- **ComfyUIが選ばれる理由（>>275）**  
  Forge Neoは最新モデル（例としてQwen-Image-2.1）に未対応だが、ComfyUIは公開前から対応している。新モデルをすぐ試すならComfyUI一択、という整理。Neoを使う人は「WebUIから離れられない」「ComfyUIの操作に慣れない」層だと見られている。
- **ComfyUIに慣れない問題と自作対応（>>280）**  
  サムネイル右クリックでエクスプローラを開く、程度は標準であってほしい、という不満。自作して解決し、少し便利になった、という話。
- **Radeonドライバ同梱（>>244）**  
  ドライバアップデータにPyTorch、ComfyUI、LMStudio、Ollamaのインストーラが付く。初心者でもすぐローカルAI環境を作れる、という導入経路の話。
- **公式WFと「Easy」要求（>>287–288, >>349）**  
  EasyQI2.1を求める声に対し、公式ワークフローを開いて指定場所に置くだけでよく、今はEasyノード時代より簡単、という反応。テンプレートのQwen2.1 WFをそのまま使っている、という報告もある。
- **i2iの解像度挙動（>>352）**  
  resolutionが0だと入力画像サイズをそのまま使うため、大きい参照画像だと遅くなる、というComfy側の注意。

## ComfyUIカスタムノード / ワークフロー

- **H3 RefMod系ノード（>>267, >>270, >>281）**  
  - Fantastic側は「Draft from Refmod」で参照関係が自動入力される。  
  - 手順の理解は、Create H3 RefMod Masterで事前作成 → Load H3 RefMods → Apply H3 RefMod。デフォルトだと破綻しやすく、ComponentsをVisualにするとマシになったが再現度はまだ弱い。  
  - 使い方は `ComfyUI-Fantastic-MiniMaxH3-PromptBuilder` のドキュメントが参考になった。
- **RefMod用プロンプト自動化の考え方（>>242, >>259, >>271）**  
  参照画像を毎回VLMでキャプション化し、メタデータとして持たせてプロンプト作成を自動化したい、という案。実装案としては、梱包画像のどれかをVLMに渡してプロンプトを作らせ、アンカー部分だけ手またはAIで直す、という流れ。
- **量子化ノード（>>437）**  
  `ComfyUI-MiniMax-H3-W4A4-VSA` は速い。12GB VRAM勢はこれで決まりかも、という選定理由。
- **音楽生成まわりのノード連携（>>277）**  
  SheetSage2のABC譜を、YuE2 Generate MusicノードとKサンプラー設定で原曲寄せに調整できる。LoRAの代替になり得るエコシステム、という見方。選ぶ理由は「似せ具合をサンプラー設定で調整できる」点。
- **ワイルドカードノード vs 自作ノード（>>330, >>336, >>351）**  
  既存ワイルドカードは「毎回ランダム」止まり。欲しかったのは、シチュ固定でカメラだけN回ランダム、リストごとに順送り／シャッフルを後から選べる、という制御。自作ノードの利点は「欲しい機能がすぐ手に入る」こと。ノード自体はChatGPTに作らせ、シチュリストはGrokに出させている。
- **プロンプトエンハンサ（>>302, >>360, >>362, >>396, >>433）**  
  - ComfyのHF側に、プロンプトエンハンサ用TE（i2i/t2i向けのQwen3.5テキストエンコーダ）が追加された。  
  - 上流のテキストノードに日本語でふわっと書き、ComfyテンプレのLLM WFを流用するとプロンプトに整う。  
  - QI2.1専用ならBenjiのカスタムノードが便利、という推薦。システムプロンプトがノード内包で、そのノード＋Clip Loaderだけで済むのが理由。  
  - ただし動かない報告もある。max_length=24000のままだと1時間近くかかりそう、1024にしても何も出ない、モジュール不足では、という切り分け。
- **背景透過ノード（>>300, >>311, >>320）**  
  アルファ背景はComfyUIノードでできる。ノードを「alpha」で探せばよい。定番としてWAS Node SuiteのImage Rembg。制約は背景を単色にしておく必要があること。生成一発で抜けるならそれでもよい、という比較。
- **Jevの自動調整（>>243, >>250）**  
  高速化比較の出し方が不公平（Attentionなし vs Jev調整あり）で、自動調整の効きはごく小さい、という批判。比較するなら「調整なしAttention vs 調整ありAttention」だ、という指摘。

## 背景除去・画像管理などの周辺ツール

- **IOpaint / クリスタ（>>299, >>303, >>315）**  
  IOpaintだと汚れやすいので、いちいちクリスタで抜いていて面倒、という不満。透過品質の比較対象として出ている。RMPGも試す、という言及あり。
- **Eagle（>>443）**  
  生成自体は2分でも、Eagleの記録だと2枚で7分。待ち時間の計測・管理に使われている。
- **自作画像ビューア（>>381）**  
  生成画像用ビューアを更新。閉じるキー、アイコンサイズ変更、起動高速化。閉じる操作はショートカットよりマウスジェスチャ推奨。
- **比較用アプリの要望（>>354）**  
  左右に並べた画像を同時更新して見比べたい。手間が少ない方法、なければ自作、という話。
- **GPT Images型の対話制作（>>384）**  
  対話式でローカルイラストを作りたい、というツール要望。既存の一発生成WFでは足りない、という意味。

## クラウドLLM（プロンプト作成・ノード作成・デバッグ）

- **Grok / SuperGrok（>>247, >>356, >>386）**  
  参照画像＋公式プロンプトガイド＋動きの指定を投げてプロンプトを作らせる、という使い方。契約理由は動画生成だったが、実際はローカル向けプロンプト作成で最も使っている。  
  **選ばれる理由:** 画像読み込み付きのプロンプト作成をローカル完結にするとVRAMが足りない。コストとVRAMを考えるとGrokが最強、という比較（>>390）。
- **Gemini vs ChatGPT（>>326）**  
  H3用プロンプト生成で、Geminiは規制の強い題材にも乗る。ChatGPT（チャッピー）はどうか、という比較。性能差の中身はログ上は未検証。
- **ChatGPTのその他の用途**  
  - ログとワークフローJSONを渡して不調の切り分け（>>348）。  
  - モデル説明書を投げてシステムプロンプトを作らせ、コピペする（>>421）。  
  - 自作ノード生成（>>330）。
- **Claude（>>405–407）**  
  全拒否の原因は、古い世代のときに入れた「性能が上がる」カスタムプロンプトの引き継ぎだった。空にしたら動いた。その後は混雑エラー。ツール設定の持ち越しが罠、という話。
- **Codex（>>435）**  
  初回LoRAの失敗箇所を見てキャプション再検討するとき有用。画像を直接読ませて改善案を出させられる。  
  **選ばれる理由:** 画像読み取り＋修正案。  
  **注意:** トークン消費が重いので、先に手動で一次選別する。

## ローカルLLM / VLM（Qwenの非画像生成を含む）

- **ローカル完結が難しい理由（>>247, >>361, >>390）**  
  画像読み込みありのプロンプト作成はVRAMを食う。24GBでも画像生成と同時起動は厳しい。LLMはVRAM容量ゲーで、このクラスは16GBでも足りない。
- **候補（>>390, >>391, >>413）**  
  - Qwen3.8 27B非検閲か、Gemma4 31B非検閲。  
  - Qwen3-VL-4B-Instructは数秒で終わるが、曖昧な指示への想像力は弱い。小さいものから試す、という方針。  
  - 以前の実用候補は `qwen3-vl-8b-abliterated-caption-it` と `qwen3-vl-8b-nsfw-caption` のQ6/Q8。プロンプト用なら超高精度は不要で、システムプロンプト次第。雑な指示は雑な返りになる。  
  - MoE＋Free TokenならVRAMなしでもいけるらしいが、実用評価はまだ不明（>>390）。
- **クラウドにローカル情報を渡したくない（>>255）**  
  ローカル環境の情報をクラウド補助に出すことへの抵抗。ローカルVLM/LLMを使う動機の一つ。

## 学習・キャプションツール

- **Kohya（>>392, >>442）**  
  Qwen2.1対応を待っている理由は「使い慣れている」こと。  
  別件で、OpenAI互換API＋VLMでキャプションするKohya製スクリプトが推薦されている。失敗もあるので手確認は必要だが、体感90–95%はそのまま使える叩き台になる。
- **AIToolkit（>>393）**  
  オフロード（ブロックスワップとは別）を100%にすると、VRAM約14GB・RAM約60GB。RAMがあれば16GB VRAMでも回せる、という選定理由。速度感は他手法の中間、という報告。
- **W14Tagger（>>434）**  
  タグ結果を参考にしつつ、キャプションは全部手で書き直している。AI任せより安定する、という理由で手作業を選んでいる。
