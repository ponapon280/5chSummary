ログから、生成AIまわりの**ツール**（UI・ノード・学習スクリプト・エージェント等）の話題だけを拾いました。指定リストの画像生成モデルそのものの性能・絵柄・プロンプトの話は除いています。webUI / nano-banana という名前の話題はありません。

## ComfyUI
- **T2Iテンプレにノード追加**（>>463）  
  デフォルト設定で、画像生成込み約120秒。
- **Prompt Enhancer用ワークフロー**（>>474, >>477, >>490, >>491, >>493, >>503）  
  - 基本はComfyUI純正ノードで動く。日本語入力、T2I/Edit切替。  
  - **Lora Manager入りを推奨**。入れない純正向け版も別途。  
  - システムプロンプトは公式ものを無検閲化したもの、という説明。  
  - 4070 Tiではプロンプト生成に約3分半で常用は厳しい、という報告と、別環境では約30秒で常用範囲、という報告。  
  - 「JSONから文字列を抽出」＝ Extract Text from JSON ノード、という確認。  
  - WFが反映されない／メタデータ消失のトラブル。上げ直しあり。  
  - 生成プロンプトが中国語になる、というツール挙動の話。
- **別端末から操作してVRAM節約**（>>497）  
  `--listen 0.0.0.0` で別端末からComfyUIを操作。オフロードはあっても解像度は厳しいので、ギリギリ生成のときやる価値がある、という理由。
- **起動オプション**（>>487）  
  `--reserve-vram` で0.6GB空けても、ブラウザ切替でCUDAではなく3D側に負荷が逃げる、という環境トラブル。
- **ハング時の対処**（>>514, >>529）  
  最新版にすると緩和される、という話。固まったらキャンセルも効きにくく、再起動している。
- **OpenPoseノード**（>>630）  
  ポーズスワップ用に挟むと意図どおりになった、という**採用理由**（ノード追加が解決手段）。
- **If/Else Switch**（>>586–587）  
  WFのモデル部分を切替式にするために使用。
- **hybrid loader**（>>588, >>592）  
  同種の仕組みをLoRA化している人がいるので、メモリを食うhybrid loaderの代わりにそちらを試す、という提案。一方で通常ローダーと使用量はほぼ同じ、という反論もあり。
- **カスタムノード vs 公式**（>>585）  
  参照動画系の切替は、カスタムノードではなく公式側が解決策を出していないか、という確認。
- **メタデータ共有**（>>558）  
  tadaupは上げるとメタデータが消えやすい。WF共有時の注意。

## Lora Manager
- Prompt Enhancer WFでは入れておいた方がよい、という推奨（>>474, >>493）。  
- LoRA Loaderは便利なのに浸透していない（>>593）。  
- 1 LoRA＝1ノードでon/offする用途には向かないと思っていたが、**LoRA Stacker**があるので多数切替に使える（>>595）。これが使われ始めた理由。

## DrawThings
- Mac mini M6で、M4比で生成が3倍以上速い（>>450）。  
- **選ばれている理由は速度**。ローカルで画像生成が実用になるか、という反応あり（>>452）。M5以降Macがローカル実用ライン、という流れ（>>459）とセット。

## 学習・実行支援ツール
- **Fizgig**（>>527）  
  動画・音声を素材に含めなければ、VRAM 8GBでもh3用LoRAが約2時間で作れる。**低VRAMで作れる**のが採用理由。局部修正程度なら誰でも作れそう、という評価。
- **kohyaの学習スクリプト／doc**（>>540, >>573）  
  - dataset.toml＋jsonl。パスは環境によるが `¥` ではなく `/`。  
  - jsonlは開始画像（references）・結果画像・英語説明。ファイル名はすべて別名。  
  - 例: 動作の前後画像をペア登録。画像サイズはVRAM/SWAP次第。4090＋400サイズ＋SWAP 35でギリギリ。  
  - 基本設定、素材10組20枚、epoch 160で4090約150分。SWAPが多いのでGPU負荷はそれほどでもない。alpha等は未研究。  
  - LoRAは動作の補助・上書き程度で、参照画像とプロンプトを真面目にやらないと効かない、という使い方の注意。  
  - 別需要が出たらkohyaのスクリプトを使う、という保留（>>573）。
- **easyReforge**（>>534）  
  1660 Superでもローカル生成をそれなりに楽しめる。**古いGPUでも回せる**のが選ばれている理由。

## 分割・3D・エージェント
- **SAM3**（>>531）  
  アニメ画風でも検出率が高いSAM3がほしい、という要望のみ。選定理由は検出率。
- **Tripo**（>>596）  
  イラストから直接3D化させると失敗したので、Tripo経由にしてから修正、という流れ。トポロジーはガチャすれば綺麗でベース向き、だがそのままは使えない。**ベースの形がよい**のが採用理由。最終的にはBlenderを覚えることになった。
- **Blender（リモート操作）**（>>594, >>611, >>645）  
  AstraのComputer Use／リモート操作でモデリング。参照を渡しても弾かれなかった、という話はあるが、**10分強でクレジットを使い切る**ほど消費が激しい。採用というより、消費が速すぎて使いにくい、という評価。
- **Astra / Sol / Luna（コーディング・レビュー用の使い分け）**（>>600, >>602, >>605, >>606）  
  - 通常作業はSol、レビューなど重い仕事はAstra、という分担。  
  - Astraは消費が速すぎるのでSolで足りる、という不採用寄り。  
  - Chat側のProで設計・指示を細かく出してからCodexに渡すと、実装側の負担が減るかもしれない、という使い方（ケチケチ運用）。
- **Codex**（>>470, >>538, >>551, >>554, >>561, >>567, >>577, >>602）  
  - 生成が異常に遅い件を聞いても原因不明。  
  - カスタムノードや生成まわりのアプリを作らせる用途。その程度ならProでも減りすぎ、という声と、ProX5でも1日で尽きる、という声が並立。  
  - リセット情報は開発者tiboのX、およびリセット監視サイト。  
  - Codexデスクトップは、Chat ProのログをそのままCodexに渡せる。  
  - **選ばれる理由は、計画・実装・ノード／アプリ作成を任せられること**。消費の速さは不満点。
- **ChatGPT（チャッピー）**（>>504, >>509）  
  参照処理の高速化を頼んだら、全体7分（サンプリング2分）が全体2分になった。**ワークフロー短縮**が使われた理由。プロンプト作成用に制限の緩い版がほしい、という要望あり。
- **OpenClaw**（>>568）  
  上位プランの枠から常時稼働。1日約50万トークン・約1000回呼び出し。画像生成は暇つぶし側で、本体はシステム開発エージェントとしての利用。

## Qwenシリーズ（画像生成以外）
指定どおり、画像生成モデルとしてのQwen-Image / QI2.1の画質・検閲・ライセンスの話は入れていません。

- **Qwen3.8-27B は意図の汲み取りが弱い**（>>489, >>492）  
  雑な説明から「こういう展開にしたい」を読む力は、Gemma4-31Bの方が段違い、という比較。  
  ベンチマークでは測れない、プロンプトを考え出す力の話。  
  ただしその汲み取りは、指示どおりだけやってほしい人には余計、という両論（>>492）。  
  **Gemmaが選ばれる理由は、曖昧な説明からの意図読みと速さ**（>>506は26B-A4Bを速度優先で使用、不満は少ない）。

画像生成そのもののモデル談義（anima、NAI、Krea、QI2.1の絵柄・エロ耐性、FL2VA/Ref2VAの画質比較、Z-Image移植など）は対象外として省いています。
