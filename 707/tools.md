## ComfyUI：動画保存ノードの高速化

標準Save VideoノードとVHS・XENodes等のNVENC圧縮ノードを比較した結果、標準ノードが30秒速いことが確認された。計測ごとにComfyUIを再起動して条件を揃えている。AV1がH.264より速く圧縮率も高い（125, 126）。

計測データ（126）:
- 標準 Save Video AV1 CRF40: 42.33秒 / 42MB
- 標準 Save Video H.264 CRF25: 61.23秒 / 50MB
- XENodes H.264 NVENC CRF25: 91.82秒 / 245MB
- XENodes AV1 NVENC CRF40: 93.96秒 / 76.3MB

1MPを2倍10秒の条件で、標準ノードは保存に40秒かかったが、自作ノードで7秒になった。全てGPU処理させている（174）。条件を明記した比較（2MP 24fps）でも標準ノードav1 crf40で42.33秒、自作ノードは7秒（H264NVENCmp4）（195, 199）。VHSのnvenc_hevc（ビットレート10, 2MP 10秒 24fps RTXVSR2倍）で7.8秒（GPU: 4080s）（202）。

VHSは1フレームずつCPUに返す仕様で遅く、音なしmp4・PNG出力をオフにしても処理時間が変わらず、動画削除分だけ処理時間が増える罠がある（220, 224, 225, 227, 228, 230, 232, 252）。

スレ有志がチャッピー（ChatGPT）に作らせた「CPU通さないNVENC保存ノード（カスタム保存ノード）」を使用すると処理が爆速になる。4080s＋codexニキのNVENCノードで4秒、同条件CPU（9900X）で20秒（203, 228, 259）。チャッピーに頼んでFilename_prefixに `%date:yyyy-MM-dd%` が使えるよう `__init__.py` を変更した件では、さらに処理時間が半分になったとの報告がある（348）。ノードの設計思想は「KISSの原則（Keep it simple, stupid）」に従っている（201）。4Mピクセル（1MPをRTXVSR2倍 10秒 24fps）でほぼ同じビットレート（約21,000kbps）の設定で比較するとVHSより2倍高速。ComfyUIのPython側のffmpegがPC側より約3.3%高速だった（219）。

NVENCはCPUエンコードと比較すると画質は悪いが高速。コマ送りしないと分からないレベルならNVENCで良い。高ビットレートではエンコーダによる差は分からないが、低ビットレートではNVENCの画質が悪いのが定説。保存を高速化してその分1stepでも上げた方が画質が良さそうという見方がある（212, 215, 216）。

## ComfyUI：MOSS-Imageネイティブ対応とワークフロー整備

mainブランチにマージされ、Load CLIPでmoss-imageが選べるようになり、カスタムモデル・カスタムノードが不要になった（475, 476）。ComfyUIを最新版にすると、動画作成後に表示されるアセットからまとめて保存するとzipでまとまるようになった（473）。Comfy kitchenのアプデでもmossに対応した（620）。

当初は公式WFがcomfyに少し足りない状態だったが、kijaiがcomfy公式WFを整備しプルリクにWFを上げた（479, 558, 567）。kijaiのbboxワークフローを読み込み、下部のbbox関連ノードを削除すれば普通のt2iワークフローになる。50stepではなく25stepでも綺麗に出た（573）。Kijai氏のWF設定はsteps25/cfg2.5/er_sde/simple。文字を入れる場合はsteps50/cfg3.0/euler/sgm_uniformの方が正確性が上がるが時間は倍になる（693）。複数ユーザーがsteps50/cfg3.0/euler/sgm_uniformに落ち着いた。25stepは少なすぎる（694, 695, 696）。Kijai氏のWFで指が溶けやすく、手の輪郭線が肌色に溶けがちで腹部や太ももと合体する（689, 691）。

Comfy謹製のMOSS-Image Layout Promptノードが追加されたが使い方が分からないという声がある（551）。ModelSamplingSD3はComfyOrg製のモデルには不要（487）。ComfyUI最新版にしたら生成が1.7倍速になった（745）。非公式ノードでは5倍遅かったが、公式ノード来てから爆速になった（806）。ComfyUI標準ノードに置き換えたら3分かかっていた生成が1分になった。VRAM 8Gの3070環境（639）。

create bounding boxesノードがNode 2.0必須のため、2.0へ移行する動きがある。Fast groups bypasserはNode 2.0でも機能自体は生存するが、トグルボタンのon/off表示が正しくない（568, 611, 639, 682, 757）。BBoxを使う/使わないケースの切り替えにIf/Else Switchノードを複数使用しているが、ミュートにはならない課題あり（655, 699）。

## ComfyUI：量子化・高速化・VRAM要件

INT8量子化版「MOSS-Image SFT (INT8 ConvRot)」がComfyUI従来のローダーで読み込める（314）。comfyのint8だとanimaと同程度の速度で出力可能。danbooruのワイルドカードやTIPOを使ったポン出しで実用的に使える（953）。comfyにMOSSでint8を使った場合に3割高速化の更新が入り、VRAM16G・MEM96G環境で確認された（656, 662）。ComfyUIのmainブランチ最新のint8 convrotとModel Sparse Attentionを適用して速くなったが、それでも遅め。stepsを減らすと画質への影響が大きいので50stepsのまま運用している（962）。bf16とint8_convrotを比較しても生成時間はほとんど変わらない（818）。

8step DMD LoRAによる高速化では、元が50stepで120秒だったのが20秒まで高速化。細部は潰れるがプロンプトお試しのガチャ用には適する（603, 608）。DMDloraを強度0.8の12stepで速度十分だが、moss8stepDMDlora使用時にCFGを落とさないと謎の車の絵を描き始める事象あり。ちょっと劣化激しくてダメな感じとの声もある（639, 839, 875）。ベースのみで10ステップで出すのと8step LoRAを使うのは微妙なところ（610）。sft用の8step DMDはもう来ている（803）。int8モデルはまだ高速化対応しているか不明。DMDはベース用か（460）。kijaiによりsftは生成が30パーセント早くなった（620）。

W4A8量子化TE（qwen3.5_9b_w4a8_gptq.safetensors）は低スペ向けの4bit系。W4A8は結構変わる（523, 526, 545）。W4A4はBF16比で差が大きいがW6A8は差が少ない。INT8昆布が優秀。W6A8のサイズはW8A8と僅差だがINT6処理が必要で速度が遅い可能性（935, 942）。

MOSSはモデル5GB・TE9GBのためVRAM12GBの4070tiだと厳しい。VRAM16GB未満には人権なさそうだが、VRAM8GBで動かしているスレ民もいる。低スペなら4bit版を使えばよい（742, 814, 816, 817）。MOSSは重く、サンプルjson試行時にはVRAM 32GBギリギリまで使用。INT8とTurboがすでにアップされている（363, 368, 372）。TEはcomfyならCPUに載せられ、evictもされるため問題ないが、9BのTEをCPUで処理するのは相当重い（833）。MOSSの公式上限は2Mピクセル。公式グラディオでは4Mピクセル（アプスケ入りか）（809）。

## ComfyUI：バウンディングボックス（BBox）機能

Anima比でBBox形式で正確に位置を指定できるのがMOSSの売り（755）。bboxはお手軽に構図を変えられて便利（829）。カラー指定が画像に反映される。JSONの指定範囲で枠を切る挙動。コマごとに処理するため4コマ×2話構成でも崩れない（915, 936, 939, 940, 945）。

ideogram4とMOSSで微妙にbboxの座標ルールが異なる。DiT的にはセンター0が良いが、手動の場合y座標を先にするのが混乱しやすい（795）。ideogram4で作成したLLM連携bbox出力ノードをMOSSのbboxルールに修正すれば使えそう（821）。Ideogram 4のBBoxはupper arm, forearm, thigh, lowerleg, torso, head等のパーツ単位で位置や向きを指定可能。nipple, breast, butt, pubic areaも個別指定できる。MOSSはそこまで細かくパーツ指定はできない（940）。

パーツ指定はrefでできるため、BBoxの構図制御は二次の書き分けやコマ割りくらいにしか使い道がないとの見方もある（954）。手足の崩れはインペイントできれいに直るため気にならない（959）。

根拠: 755, 795, 821, 829, 915, 936, 939, 940, 945, 954, 959

## テキスト・音声ツール：EmojiTTS / IrodoriTTS

EmojiTTSv4は絵文字キャプション＋音声分析キャプション機能が追加。APIはLM Studio（ローカル）。絵文字キャプションをオフにしてもログに「絵文字キャプション開始」と出るバグがある。lora学習タブのマニフェストファイル(.jsonl)が空欄のままだと学習エラーになる。学習したloraは直下フォルダに作られるが、loraフォルダ内に入れないと使えない。EmojiTTSv4のlora学習はv3のまま更新されておらず、生成すると中国語を長々と話すバグがある（164, 170）。

IrodoriTTS v4sはlora学習したら前回は1時間/1000stepだったのが今回は10分/1000stepで終わった（チャッピーに聞いて設定を作成）。ファイル容量はともかく作り直しのハードルが下がる。MAX3000stepまで試す予定（176, 177, 184）。LoRA学習のstep数比較: 1000で充分、2000で微妙に良い気がする、3000で声はかなり似るが音割れが起きやすい（音割れはシード次第）（184）。

strata + deepseek harnessでuncensoredなモデルを使い、複数カットを繋ぐ系のMiniMax3（H3-Multishot-Workflow）のワークフローでプロンプトを作成させると、3分くらいのAVが作れる。ローカルLLMのエロプロンプト力が段違い（83）。minimax長尺作成にExtenderを使っているが、元の参照15秒制限のせいでいまいち（180）。H3の長尺や高速化のワークフローが雨後の竹の子のように乱立しているが、多すぎて選べない。中国語のwf（latent使用）は厳しい（194, 198）。

Krea3はAPIで利用可能であり、ComfyUIも対応済み（200）。

根拠: 83, 180, 194, 198, 200

# 総評

1. ComfyUIの動画保存ノードは、標準ノードがVHSやXENodesより高速であることが条件を揃えた計測で確認されたが、さらにチャッピー（ChatGPT）に作らせたCPU通さないNVENCカスタムノードがVHS比で2倍高速を達成し、エンコード処理のボトルネック解消にLLMエージェントが直接貢献した。

2. MOSS-ImageのComfyUIネイティブ対応がmainブランチマージによって完了し、カスタムノード不要化と公式ノード爆速化が同時に進行した。kijaiによるWF整備とINT8量子化により、VRAM16GB環境でもanima同程度の速度でポン出しが実用的に可能になった。

3. MOSSのBBox機能はパーツ単位の位置指定にLLMエージェントが必須となっており、CodexやチャッピーにJSONテンプレート作成・プロンプト自動生成・環境構築を丸投げする運用が定着している。ワークフローに抵抗があるユーザーはForge Neo拡張で回避し、低スペユーザーはCivitaiオンライン生成・トレーニングに流れる棲み分けが形成された。

4. EmojiTTS/IrodoriTTSのLoRA学習時間がチャッピー作成の設定で1時間から10分に短縮され、作り直しのハードルが下がった。テキスト・音声ツールでもLLMエージェントによる設定最適化が効率化の鍵となっている。
